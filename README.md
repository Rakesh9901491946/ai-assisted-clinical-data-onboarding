# AI-Assisted Clinical Data Onboarding

A review-first workflow for profiling synthetic/partner CSV files, proposing clinical field mappings, validating them, and exporting clean OMOP-shaped data through OpenRouter free models; no code generated by the model is executed.

## Start with Docker

Requirements: Docker Desktop with Compose.

```sh
cp .env.example .env
# Optional: add OPENROUTER_API_KEY and OPENROUTER_MODEL to .env
docker compose up --build
```

Open the Streamlit app at [http://localhost:8501](http://localhost:8501). The API runs at [http://localhost:8000/docs](http://localhost:8000/docs). PostgreSQL is exposed on port 5434. Use any of the three synthetic samples under `data/samples/` to try the workflow.

The app also works without an API key using deterministic header suggestions. With a key, choose OpenRouter suggestions; if the provider fails and deterministic suggestions are available, the API falls back to those. Human approval remains mandatory in either path.

## Deploy to Streamlit Community Cloud

Push this project to a GitHub repository and create an app from `app.py` on [Streamlit Community Cloud](https://share.streamlit.io/). Community Cloud installs packages from the root `requirements.txt`. Without `API_URL`, the Streamlit app calls the FastAPI handlers in-process, so it does not need separate API or PostgreSQL services. The local Docker Compose setup continues to use the separate services.

Add this to the app's Secrets settings (Advanced settings during deploy, or App settings afterward):

```toml
OPENROUTER_API_KEY = "your-openrouter-api-key"
OPENROUTER_MODEL = "openrouter/free"
```

Keep the GitHub repository and Streamlit app private for partner data. Cloud mode keeps active rows in app memory and does not persist upload/audit records to PostgreSQL; a restart clears active sessions. This demo is not approved for real patient data or production use.

## OpenRouter free API key

Create a key at [OpenRouter](https://openrouter.ai/keys), then set it in `.env`:

```dotenv
OPENROUTER_API_KEY=your-key
OPENROUTER_MODEL=openrouter/free
```

The free plan currently lists 25+ free models and a limit of 50 requests/day. Free model availability and rate limits can change; set `OPENROUTER_MODEL` to a currently available free model when needed. See [OpenRouter pricing](https://openrouter.ai/pricing/) and [API docs](https://openrouter.ai/developers).

## Workflow

1. Upload one of the sample CSVs or another CSV and enter a partner name.
2. Review the source preview, missingness, distinct counts, date parseability, and duplicate count.
3. Generate deterministic and/or OpenRouter mapping proposals. The provider receives column headers and aggregate dtype/missingness only; it does not receive CSV rows or cell values.
4. Edit targets/transforms and explicitly approve mappings.
5. Run the allowlisted transform and inspect Pandera/business-rule validation errors.
6. Download the validated CSV after it passes validation.

## API endpoints

- `POST /uploads`: upload and profile CSV.
- `POST /uploads/{id}/mappings?use_ai=false`: deterministic rules only; set `use_ai=true` to request OpenRouter suggestions.
- `POST /uploads/{id}/approve`: submit reviewed mapping proposals and approval flags.
- `POST /uploads/{id}/transform`: execute approved mappings; optional `send_to_omop_staging=true` writes to Project 1 raw staging.
- `GET /uploads/{id}/download`: retrieve validated CSV.

## Connect to Project 1

Start Project 1's PostgreSQL service first. Add this setting to this project's `.env` (the host port is 5433 by default):

```dotenv
OMOP_DATABASE_URL=postgresql://clinical:change-me@host.docker.internal:5433/clinical
```

Use `POST /uploads/{id}/transform?send_to_omop_staging=true` after human approval. This writes normalized source rows to `raw.partner_omop_staging`. Then rerun Project 1's dbt pipeline to materialize those partner rows into OMOP. The default app workflow does not write to Project 1 unless explicitly selected.

## Data safeguards and known limits

- The LLM prompt contains only header names and aggregate profile metadata. Never provide real patient data in a way that includes patient values to an external model; the current implementation does not send them.
- Upload preview and transformation occur in this app. The demo is not a production HIPAA compliance claim; production deployment needs access control, TLS, retention controls, threat modeling, and organization-approved vendor terms.
- PostgreSQL stores upload metadata and audit events; CSV rows and mapping sessions are held in API process memory, so restart loses active sessions. Use one API instance for this demo.
- The OMOP integration writes source values to Project 1 raw staging. Project 1 must be configured to include partner staging in its downstream person/condition models before those records appear in final OMOP tables.
- Clinical terminology mappings are not inferred or fabricated; retain source code and run authorized terminology mapping in the downstream pipeline.
